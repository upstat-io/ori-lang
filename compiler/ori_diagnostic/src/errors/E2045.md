# E2045: Post-Condition Contract Must Be a Lambda

A `post(...)` clause was attached to a function whose argument was not a
lambda binding the result. Post-condition predicates run after the function
body and need a name for the returned value, which is only well-formed as a
lambda parameter:

```ori
post(r -> r > 0)                    // OK — single-result lambda
post((from, to) -> from + to == 100)  // OK — destructured tuple result
```

## Cause

The parser enforces this shape at syntax time and emits E1002 when the
`post()` argument is not a lambda, so E2045 is reserved as a stable code in
the diagnostic catalog and is not reachable from the type checker today. The
code exists so that:

- The error code range stays gap-free as new contract diagnostics are added.
- Future surface changes (e.g. a `post()` form that takes a non-lambda
  expression and desugars it) can move enforcement into the type checker
  without renumbering.

## Cure

If you see E2045 emitted from any toolchain, file a bug — the parser path
should have caught the malformed `post()` first. The user-visible cure is
identical to the cure for E1002 on a `post()` clause: rewrite the argument
as a lambda binding the result.

```ori
@balance () -> int
    post(b -> b >= 0)            // OK — single-result lambda
    = { ... }
```
