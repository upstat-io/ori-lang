# E2049: EVALUE_DROP_CONFLICT — Type Marked `Value` Cannot Implement `Drop`

A type carries the `Value` marker AND declares an `impl T: Drop { @drop ... }`
block. `Value` and `Drop` are mutually exclusive: `Value` semantically declares
the type as inline-stored with bitwise copy and no ARC, so the refcount-zero
cleanup path that `@drop` hooks into never fires for `Value` types — the
declared `@drop` body would never be invoked.

## Cause

The shape rejected pairs `Value` with `Drop` on the same type, regardless of
which declaration source-orders first:

```ori
// Order A — Value-on-type-decl FIRST, Drop-impl SECOND
type Point: Value, Eq = { x: int, y: int }

impl Point: Drop {
    @drop (self) -> void = print("dropping point")  // ERROR: E2049
}
```

```ori
// Order B — Drop-impl FIRST, Value-on-type-decl SECOND
impl Point: Drop {
    @drop (self) -> void = print("dropping point")
}

type Point: Value = { x: int, y: int }              // ERROR: E2049
```

Per `ori-syntax.md §Prelude` (Value trait section): `Value` is a marker trait
that asserts inline storage, bitwise copy, no ARC, and no `Drop`. The compiler
realizes `Value`-typed values with stack-resident layout and no refcount
header; `@drop` would have no hook to run from.

Distinct from `E2029` (`Hashable` requires `Eq`), which fires at the derive
registration surface. `E2049` fires at the TWO non-derived registration
surfaces because `Drop` is explicitly-implemented (no auto-derive per
`drop-trait-proposal.md §Auto-derive`) and `Value` lives on the type
declaration (compiler marker, not user-implementable via `impl T: Value`).
Whichever registration lands second emits the diagnostic; the span points at
the second registration.

## Cure

Three idiomatic resolutions:

1. **Remove `Value` from the type declaration** — the type carries heap state
   or owns resources that benefit from `Drop`'s cleanup hook, so it should be
   ARC-managed and not `Value`:

   ```ori
   type Point: Eq = { x: int, y: int }   // dropped the Value marker

   impl Point: Drop {
       @drop (self) -> void = print("dropping point")
   }
   ```

2. **Remove the `impl T: Drop` block** — the type's fields are all primitives
   / `Value` types and no cleanup is needed; bitwise copy semantics are
   sufficient:

   ```ori
   type Point: Value, Eq = { x: int, y: int }   // kept Value marker
   // (no impl Point: Drop block)
   ```

3. **Split the responsibilities into two types** — one carries the `Value`
   marker for inline storage of the structural data, and a separate type
   owns the resource and carries `Drop`:

   ```ori
   type Coords: Value, Eq = { x: int, y: int }

   type Tracked = { coords: Coords, name: str }

   impl Tracked: Drop {
       @drop (self) -> void = print(`dropping {self.name}`)
   }
   ```

Per Annex E §AIMS and the spec `Value` clause, the marker invariant is that
`Value` types participate in lattice-driven analysis as bitwise-copy values
with no RC traffic — `Drop` would re-introduce the refcount-zero callback
that `Value` was declared to elide.
