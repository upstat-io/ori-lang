# Section 05: Builtin Method Architecture

**Status:** Complete
**Goal:** Builtin method codegen uses a declarative dispatch table. Every `TYPECK_BUILTIN_METHODS` entry is proven to have a codegen handler.

**Context:** The 7 submodules in `arc_emitter/builtins/` (2,425 lines total) hand-code the same patterns: extract receiver, match method name, emit inline IR. There's no shared abstraction. The DPR identified that three independent registrations (`TYPECK_BUILTIN_METHODS` in `ori_types`, `eval_builtin_method()` in `ori_eval`, and `try_emit_builtin_method()` in `ori_llvm`) can silently drift. Swift avoids this because methods are just functions; Lean avoids it because builtins are runtime calls. Ori's inline codegen is faster but needs structure.

**Implementation Note:** The chosen architecture uses a `declare_builtins!` macro rather than the originally planned `register()` pattern. The macro generates BOTH a `dispatch()` function AND a `REGISTERED` const from a single list of entries — a compile-time sync guarantee that the registration and match cascade can never drift apart. The `BuiltinTable` aggregates all submodule registrations into a `LazyLock` singleton for O(1) lookup in sync tests. This is superior to the planned runtime `register()` approach because it catches sync errors at compile time, not test time.

## 05.1 Define BuiltinTable Abstraction

**File:** `compiler/ori_llvm/src/codegen/arc_emitter/builtins/mod.rs`

- [x] Define the `declare_builtins!` macro that generates both `dispatch()` and `REGISTERED` from a single list:
  ```rust
  macro_rules! declare_builtins {
      ($emitter:ident, $ctx:ident; $( ($type_name:expr, $method:expr, borrow: $borrow:expr) => $body:expr ),*) => {
          pub(super) fn dispatch<'scx: 'ctx, 'ctx>(...) -> Option<ValueId> { ... }
          pub(super) const REGISTERED: &[BuiltinRegistration] = &[ ... ];
      };
  }
  ```

- [x] Define `BuiltinRegistration` struct (type_name, method_name, receiver_borrowed)

- [x] Define `BuiltinCtx` superset context struct for uniform handler interface

- [x] Define `BuiltinTable` with two-level `FxHashMap<type_name, FxHashMap<method_name, registration>>` for O(1) lookup (two-level because tuple keys can't use `Borrow` for non-static lookups)

- [x] Implement `BuiltinTable::build()` collecting from all submodule `REGISTERED` arrays

- [x] Store as `LazyLock<BuiltinTable>` singleton (`builtin_table()`)
